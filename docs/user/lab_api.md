# Lab HTTP API (`/api/v1/lab`)

Status: implemented in G2 (2026-10-30), hardened after the independent review (G2b). Contract: `docs/design/lab_api_contract.md` (its change log lists deviations). Source: `src/api/lab_api.rs`, declared inside `src/api/server.rs`. Tests: `tests/integration/lab_api/` (run through the `lab_live_scenario_b_tests` target). **Review status: the first independent review (no Critical/High) is incorporated; a second review of the G2b changes is pending.**

The API starts the same experiment code as the tests and the `phantom-lab` binary: `lab::runner::execute` (kind `t1_matrix`, tier SIMULATED) and `lab_live::scenario_b::run_experiment` (kind `scenario_b`, tier MEASURED_LOOPBACK, real gateway child processes on loopback). It has no second implementation and returns no canned results.

## Enabling it (off by default)

| Key | Default | Meaning |
|---|---|---|
| `PHANTOM_LAB_ENABLED` | `false` | When false no `/api/v1/lab` route exists (404). |
| `PHANTOM_LAB_DIR` | `lab-results` | Lab root. Runs: `<dir>/runs/<run_id>/`. Retained experiments under `<dir>` are read, never written. |
| `PHANTOM_LAB_GATEWAY_EXE` | this executable | Binary spawned by `scenario_b`. When set it must be a readable regular file (checked by the configuration preflight; `--check-config` reports it). A debug binary makes the run EXPLORATORY. |

Fail-fast rules (configuration error, exit code 2): with `PHANTOM_LAB_ENABLED=true` and no `PHANTOM_JWT_SECRET` the bind address must be loopback; `PHANTOM_SEALED_SALT_HEX` must not be present in the process environment (the library validator would read it to derive the sealed seeds, so a process serving the Lab API refuses to start with it). Run the sealed evaluation in a separate process.

## Security model

* JWT enabled: reads (`GET`) need `Observer` (`telemetry:read`), `POST /runs` and `POST /runs/{id}/cancel` need `Operator` (`scenario:operate`); `admin` satisfies both. **An Operator-only token cannot read** (Observer is a separate role; such a request gets 403). 401 = missing/invalid/expired token, 403 = insufficient role (same bodies and headers as the other control endpoints). No tenant claim is required (same as `/api/control`).
* Authentication happens first. A request that fails it is answered before the body is read or parsed and before anything is created. An SSE stream is closed when the token that opened it expires (checked at least every 2 s).
* JWT disabled (development): routes are anonymous and allowed only on loopback. `capabilities.security_mode` says `anonymous_dev_loopback_only`. In this mode every request must carry a `Host` of `127.0.0.1`, `localhost`, `[::1]` (or the bind IP) with the bind port, else 421; a request with an `Origin` header must have the same origin as its Host (scheme `http`, or `https` when ingress TLS is configured) or an origin in `PHANTOM_CORS_ORIGINS`, else 403. Duplicate `Host` headers and trailing-dot hosts (`localhost.`) are refused. This defeats DNS rebinding and cross-site requests from arbitrary pages. It does **not** defend against: a reverse proxy on the same host (it connects from loopback with an allowed Host and defeats "loopback only"), any local process, or the origins you allowlist: the development CORS profile allows `http://localhost:3000` and `http://127.0.0.1:3000`, so a page served there retains full anonymous Lab control in dev mode. Use JWT whenever anything else runs on the machine. With JWT enabled the Host/Origin check is not applied (the bearer token is the defence; browsers do not attach it cross-site).
* Both POST routes require `Content-Type: application/json` (415 otherwise), which forces a CORS preflight for browsers. CORS follows `PHANTOM_CORS_ORIGINS` (`Last-Event-ID` is an allowed request header).
* No credentials in URLs. The SSE stream must be consumed with `fetch` streaming and an `Authorization` header (resume with a `Last-Event-ID` header); the `EventSource` URL form cannot carry credentials and is not supported.
* Error bodies are generic: `{"schema":"lab-1","error":{"code","message"}}`, no filesystem paths. Server filesystem paths are also redacted (`<server-path>`, `<path>`) from every JSON payload, JSON artifact and event the API serves or writes: known prefixes (lab root, repo root, gateway exe, temp dirs, in every slash and `\?\` form) are replaced first so paths containing spaces go whole, then drive and UNC paths, in values and object keys; a value that is itself a path is replaced entirely. CSV artifacts are not scanned (they carry no paths) (run and evidence detail, `manifest.json`, `summary.json`, `run.json`); the on-disk files keep them.
* Sealed seeds: `seed_set` S/`sealed` (any case/spacing) and family `W-SF` are refused (422). The API never exposes seeds: the library validator may read the sealed salt from the environment, which is why the process refuses to start with it (above); evidence payloads are assembled from whitelisted fields and scrubbed of `seed_values`/`seeds`-type keys.

## Limits

Body <= 16 KiB (413) and must arrive within 5 s (408). Unknown JSON fields (top level, spec) -> 422; invalid JSON -> 400. `t1_matrix`: `seed_set` T or D, `n_seeds` <= 30, <= 64 ids per list, estimated cells <= 20,000, ids from the runner catalogue, `W-Z(alpha)` needs a finite alpha in (0, 10], `name` `[A-Za-z0-9._ -]{1,64}`; `out_dir` and `overwrite` cannot be supplied. `scenario_b`: `repetitions` 1..=30, `warmup_s/healthy_s/degraded_s/recovery_s` 1..=60, `arms` distinct values of `BASE`, `STATIC-CAP`, `AIMD-CAP`, `rate_rps` 1..=2000, `n_keys` 10..=100000, `static_cap/aimd_min/aimd_max` 1..=1000; no seed field. One active run (409). At most 16 concurrent SSE streams (429). Artifact download <= 64 MiB (413); non-JSON artifacts are streamed in 64 KiB chunks. Index reads cover the newest 200 entries; `limit` 1..=200 (default 50), `offset` >= 0, anything else 400.

## Routes

| Method, path | Role | Result |
|---|---|---|
| `GET /capabilities` | Observer | kinds, limits, build profile, `scenario_b.available` (+ `reason`), predicted label, active run |
| `GET /evidence`, `GET /evidence/{id}` | Observer | retained experiments (read-only), verdict snapshot, artifact names (not downloadable); Scenario B detail carries the binding interpretation notice text and limitations |
| `POST /runs` | Operator | `{"kind":"t1_matrix"\|"scenario_b","spec":{...}}` -> `202 {run_id}` |
| `GET /runs`, `GET /runs/{id}` | Observer | persisted index / state, spec, progress, timestamps, exit code |
| `POST /runs/{id}/cancel` | Operator | cooperative; `202` first time, `200 changed:false` afterwards |
| `GET /runs/{id}/events` | Observer | SSE |
| `GET /runs/{id}/artifacts`, `/artifacts/{name}` | Observer | allowlisted names with size and SHA-256 / download |

Run states: `queued`, `running`, `cancelling`, `completed`, `failed`, `cancelled`, `interrupted`. The state machine is monotone (`queued` -> `running` -> `cancelling` -> terminal); a terminal state is never overwritten. `run_id` = `YYYYMMDDTHHMMSSZ-xxxxxxxx` (UTC time + random hex; never a seed).

### Events

`event:` is one of `state`, `progress`, `result`, `done`, `error` (there is no `log` event); `id:` is monotonic per run starting at 1 without gaps; `data:` is JSON and carries `tier` where numbers appear. All events of a run are appended by one writer under one lock, one whole line per write. The stream is a tail of the persisted `events.jsonl` (resume with `Last-Event-ID`; a finished run replays and ends after `done`). A comment line `heartbeat` is sent every 15 s. Events are only those the runner produced, plus the `cancelling` state mark the cancel request writes and, after a restart, the `interrupted` marks (data `source: server_recovery_on_startup`). T1 `progress` events are throttled to about one per 200 ms (first and last always emitted). A runner crash yields `failed`; the server never fabricates `completed`.

### Artifacts

Fixed allowlist per kind, looked up by exact name (the client string is never joined to a path): all runs `run.json`, `events.jsonl`; `t1_matrix` `cells.csv`, `manifest.json`, plus `requests.csv`, `fetches.csv` when `record_raw`; `scenario_b` `summary.json`, `manifest.json`. Symlinks, junctions and other reparse points are never listed or served, at the file level and at the `t1/` and `out/` directory level; the file is opened first and its type and size are taken from the open handle. Per-repetition Scenario B files are not exposed. SHA-256 values are computed once when the run ends and stored in `run.json` (`artifact_index`); the listing only stats files. A hash is reported only while the file still has the recorded size; `run.json` and `events.jsonl` are live and not hashed. For JSON artifacts the hash is of the SERVED bytes (server paths redacted), not of the file on disk.

### Persistence, restart and child processes

`run.json` is written atomically (unique temp file created with `create_new`, flushed, renamed; failures are logged and counted in `persistence_errors`) and carries the terminal state; the terminal `run.json` is written before the single run slot is released, both under one lock, so a client that sees a terminal state and starts the next run is not refused. On startup every run among the newest 200 whose state is `queued`, `running` or `cancelling` is rewritten to `interrupted` (`exit_code` null, `error.code` `interrupted`) and gets `state`/`done` events (not duplicated if the log already ends with `done`; recovery is idempotent). A torn last line (crash mid-write) is left in place and the recovery events start on a new line; the last event id is read from the last 64 KiB only. Nothing is resumed or reported completed.

Gateway children: on Windows, when `PHANTOM_LAB_ENABLED=true` the gateway process joins a job object with `KILL_ON_JOB_CLOSE` (hand-declared Win32 FFI, no new dependency, see `bind_children_to_process_lifetime`), so children spawned afterwards die when the gateway exits, including a crash or kill; if the job cannot be created (for example a parent job forbids nesting) a warning is printed and children are only tied by `kill_on_drop`. On startup recovery, a recorded `gateway_pid` of an interrupted run is terminated only if ALL of these hold: it is not this process or one of its ancestors; the creation time (FILETIME) recorded in `run.json` (`gateway_created_ft`, captured when the run first reported that child) equals the live process's creation time exactly (a recycled pid, a sibling gateway or the API itself never match); its image path equals the configured gateway executable (case, `\?\` prefix, slash and 8.3 forms normalised); and that creation time is not before the run start. Otherwise it is not touched. The outcome is recorded in `run.json` under `recovery.gateway_reap` (`terminated`, `not_running`, `access_denied_not_touched`, `image_mismatch_not_touched`, `start_time_mismatch_not_touched`, `no_creation_time_recorded_not_touched`, `self_or_ancestor_not_touched`). Only runs under this service's own lab root are examined. Runs from before this release carry no creation time and are never reaped. Non-Windows platforms: neither mechanism is implemented; children rely on `kill_on_drop` and a hard-killed API process can leave a gateway child behind.

## Scenario B labelling

New runs carry the wording fixed by G1 disposition D1 in `summary.json` (`label_meaning`, `interpretation_notes`, `limitations`) and `manifest.json`. `VALID` means only: release driver and gateway (the gateway profile is read from the directory directly above the executable, `target/<profile>/`; any other location counts as not release), >= 10 repetitions, BASE and at least one capped arm present, the registered caps and origin parameters unchanged (static cap 24; AIMD 12-32, p99 ceiling 60 ms, window 30; cache budget, origin service time, multiplier, error rate, max-age, SWR/SIE and Zipf alpha at their defaults; any change adds a reason), workload within tolerance of the documented experiment (each phase >= half of 8/5/10/8 s, arrival rate and key catalogue within 0.5x..2x of 300 rps and 5000 keys; otherwise the reason `deviates_from_retained_experiment_parameters` is added), one host, scripted origin. Debug builds are always `EXPLORATORY`. AIMD-CAP may behave as a static cap near its minimum; canary-vs-off is not a clean A/B; all-request latency includes 503 sheds; origin-p99 is untestable with the scripted origin; stale-serving is not exercised; caps are not pre-registered. Retained artifacts are not edited; `docs/demo/scenario_b_interpretation_notice.md` remains binding for them (the API serves it with server paths redacted).

## Known limits (not verified or not covered)

The run handle's locks are held during `fsync`/rename (about milliseconds); handlers take them only on blocking threads, and a latency test bounds the effect, but a stalled disk would stall those handlers. No rate limiting or total-disk quota for runs; anonymous mode is defended by Host/Origin checks only (see above); one process-wide service (no per-tenant isolation); T1 cancellation takes effect at the next cell boundary; cancelling a run that is already writing its final state may end `completed`; the 15 s heartbeat is not exercised by an automated test; a release-build Scenario B API run was not exercised; the job object is unverified on non-Windows and when the process is already inside a non-nestable job; a worker panic outside the runner is caught and marks the run `failed` but is not covered by a test.
