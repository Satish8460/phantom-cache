# Limitations

Stated plainly so that nothing here is mistaken for a claim.

- **Adaptive benefit is not established.** No result shows that Phantom Intelligence (`observe`, `advisory`, `canary`, `active`) improves latency, hit ratio or origin load. Treat the adaptive modes as experimental: `canary` and `active` are rejected at startup unless `PHANTOM_ALLOW_EXPERIMENTAL_INTELLIGENCE=true`, and nothing in the product applies an adaptive decision. The static origin cap `PHANTOM_ORIGIN_CAP_MAX` is different: it is a plain fixed limit on concurrent origin fetches, enforced in every mode (503 when full), and it bounds origin concurrency only; it says nothing about latency or hit ratio, and it is not adaptive. The legacy `src/control/pie.rs` is a threshold stub and is not wired in.
- **No performance numbers are published with this release.** Numbers elsewhere in the repository are debug-build, loopback, single-host or simulated; none is a release-grade measurement.
- **Serving model.** On a single gateway, GET is served from the local cache or the origin. In the mTLS cluster configuration a local miss first asks the key's primary peer (peer read-through, `src/api/server.rs` around line 1735) and stores what the peer returns (a "peer fill"); there is no shared global cache. A peer-filled copy keeps the source entry's status, Content-Type, ETag, age and remaining lifetime (batch B1); see "Peer fill freshness" below for what is and is not covered.
- **Cluster mode is experimental.** In the mTLS cluster configuration the local cluster node shares the gateway's HTTP serving cache, so invalidation frames received from peers purge it (`src/main.rs:332`). A local GET miss asks the key's primary peer first (peer read-through, see "Peer fill freshness") and then the origin; there is no shared global cache. An anti-entropy reconciliation worker runs every 250 ms in cluster configurations (`src/main.rs:375`, `:383`); the burst and dead-peer behaviour was exercised in batches A and B1, its effectiveness beyond that is not established. The insecure/partial cluster configuration (`PHANTOM_ALLOW_INSECURE_CLUSTER` without full mTLS material) has no peer addresses: no invalidation frame is sent or received, and DELETE returns a gateway timeout (`src/main.rs:381`). Membership is static. See "Cluster invalidation durability" below.
- **Staleness.** Entries expire by origin headers (`s-maxage`, `max-age`, `Expires`) or, when the origin gives none, a fixed 60 s default (`PHANTOM_DEFAULT_TTL_MS` is validated but not honored: `src/config.rs:115-116`, literal `60_000` at `src/api/server.rs:1405` and `:1688`). **Origin-supplied lifetimes have no gateway ceiling** (`src/core/freshness.rs:263-276`), and the hard stale cap `PHANTOM_MAX_STALE_MS` limits only how long an expired entry may be served stale (stale-while-revalidate / stale-if-error), not the freshness lifetime. No linearizability or bounded-staleness guarantee beyond that is claimed.
- **Dashboard.** Parts of the SSE stream and UI are synthetic when `PHANTOM_SIMULATION=true`; simulated values are labeled and are not measurements.
- **Shutdown.** No in-flight connection draining yet (see operate.md), and no drain of pending cluster invalidations (`src/main.rs:509-514`; see "Cluster invalidation durability" below).
- **Idle CPU.** The lazy-reclamation sweeper task is started with a shutdown channel whose sender is dropped immediately. An idle process was observed using more than one core of CPU (single runs: debug build about 6.5 CPU-seconds in about 5 s wall; release build 14.8 CPU-seconds in 10 s wall, Windows 11, loopback, no traffic). The probable cause (a `watch::changed()` that is always ready in the select loop) was identified by code reading and has not been isolated experimentally; only single runs exist (no repetitions or intervals).
- **Platforms.** Only Windows x86-64 has been exercised.
- **Not provided:** Prometheus `/metrics` export, TLS certificate hot reload, runtime configuration reload, token revocation, container image, SBOM, dependency advisory scan, code signing.

## Peer fill freshness

Status: **fixed in batch B1 (PC-AUTO-041/042) and measured** (2026-10-31): in-process by `test_peer_fill_staleness_and_invalidation` and `test_peer_fill_preserves_status_and_binary_body` in `tests/unit/wp3_tests.rs` (real gateway HTTP handler, real peer read, real cluster invalidation; the clock is simulated by passing `now_ms`), and over real processes by `scripts/cluster_peer_fill_staleness.mjs` and `scripts/cluster_outcomes_check.mjs` (release build, Windows 11, loopback, three gateways with mutual TLS, one key, one hop, single runs; the numbers are in the batch B1 handover on the engineering board).

**What happens now.** On a local miss, a gateway whose key is owned by another member sends a `PeerReadRequest` to the primary (`src/dist/frame.rs`, `src/dist/node.rs`, `src/dist/router.rs::read_entry_from_peer`). A primary that holds a FRESH entry answers with the full entry: status, `Content-Type`, `ETag`, validators (`Last-Modified`, `must-revalidate`, `stale-while-revalidate`, `stale-if-error`), the body as raw bytes, the entry's age and its remaining lifetime. Times travel as relative durations, so the two hosts' clocks do not matter. The asking gateway stores the entry as the source had it (`created_at` is moved back by the age, the lifetime is age plus remaining lifetime, minus the transfer time), so:

- the filled response has the primary's `Content-Type`, `ETag` and status (a `text/plain` body is no longer served and cached as `application/json`, a binary body is no longer re-encoded as text), and `Age` is the age of the source entry;
- the peer copy expires when its source expires (the in-process test allows a drift of 1.5 s; the process script allows `--tolerance-s`, default 3 s, because it polls once per second); it never outlives its source by the old fixed 60 s;
- a peer that answers `Miss` (nothing fresh, or the peer is Recovering or Suspect, or the entry is larger than one 1 MiB frame) sends the request to the origin. Such events are counted in `metrics.outcomes.peer_reads_without_hit`.

**Bounds and ordering (batch B2).** A lifetime sent by a peer is clamped to 24 h, and an age or lifetime of more than a year makes the gateway ignore the entry and ask the origin (`metrics.outcomes.peer_reads_without_hit.rejected_lifetime`). Peer reads go to the key's primary only: there is no fallback to a replica, because a replica can lag behind an invalidation that the primary already applied; if the primary cannot be reached the request goes to the origin. DELETE purges the local cache a second time after the cluster leg, so a GET that raced the DELETE and peer-filled the entry cannot leave it on the gateway that answered the DELETE (read-your-delete on that gateway); other gateways see the invalidation when the purge message arrives, normally within milliseconds, and this window is not bounded by a measurement.

**Version guard.** The peer-read payloads start with a format byte (`PEER_ENTRY_FORMAT`, currently 1). A peer that knows the message but not the format answers `Unsupported`; a build that does not know the message type (older than batch B1) closes the connection. In both cases the asking gateway refuses the answer, never guesses at a layout, and goes to the origin; a refusal is counted as `refused_format` only when the peer answered. Mixed-version clusters therefore degrade to origin fetches, not to wrong data. Rolling upgrade: after the upgrade of one node, peer reads to or from not-yet-upgraded nodes fall back to the origin until all nodes run the same build.

**What is still not bounded or not measured.**
- A chain (a peer-filled entry later used as the source for a third gateway) keeps the original age and remaining lifetime, so it cannot extend the lifetime; this was reasoned from the code and covered by the age arithmetic, not measured over three hops.
- Bodies larger than one frame (1 MiB) are not peer-filled.
- Stale-while-revalidate: the peer read path returns only entries that are still fresh, so a stale entry is never copied; the validators are carried so the copy can itself serve stale-while-revalidate within its own window. Not measured with stale serving enabled over the cluster.
- Transfer time is subtracted from the remaining lifetime (measured at the asking gateway); queueing before the peer read starts is not.
- One host, loopback, Windows only; no performance claim.

## Cluster invalidation durability

Status: code reading (2026-10-31) plus the batch A and B1 tests; no test kills a gateway process that still owes invalidations.

**What a 204 from `DELETE /api/v1/cache/<key>` means in a cluster.** The issuing gateway purged its own cache first, and the key's primary (or the acting primary on failover) acknowledged within a 150 ms leg (`src/dist/router.rs::invalidate_key_across_cluster`). Every other configured member is invalidated afterwards by an in-memory background broadcaster: one bounded queue per destination, at most 4 deliveries in flight per destination, up to 4 attempts per delivery (1 attempt if the destination is already known to be unhealthy; one probe per 500 ms while it is unreachable). Deliveries that give up are counted in `metrics.cluster.broadcaster.exhausted`; a destination queue that overflows is counted in `dropped`. A DELETE answered `503 PrimaryInvalidationBusy` means this gateway's connection pool to the primary was saturated; the invalidation is still delivered in the background.

**Repair.** Every fan-out delivery also writes a record into a bounded in-memory ring buffer (`src/dist/anti_entropy.rs`, 4,096 records or 4 MiB). A peer that detects a gap in the sequence numbers it receives, or that is marked Suspect or Recovering, pulls the missing records from the sender's ring buffer (the anti-entropy worker, every 250 ms, `src/main.rs`). If the needed history was already overwritten, the peer flushes its whole cache. There is NO persistent repair ledger and NO separate repair worker in this release; an earlier version of this document described them, and they are not in the code.

**Failure model.** Undelivered invalidations and the ring buffer exist only in the memory of the issuing gateway process. If that process crashes, is killed, or receives SIGTERM/Ctrl-C before a peer has caught up, the records are lost: shutdown does not drain them (`src/main.rs`), and a restarted gateway starts with an empty ring buffer; peers do not detect the restart as such. A peer that missed the invalidation keeps serving the old entry until it expires (origin freshness lifetime, or 60 s if the origin gave none; origin lifetimes have no gateway ceiling) or until another DELETE of that key reaches it. Out of scope for this statement: disk loss, and partitions longer than the ring buffer history.

**So: a 204 is not proof that the object is gone from every gateway.** Do not rely on it for deletion-critical content (legal removal, privacy erasure, revoked content) without the measures below.

**Operator guidance.**
- For deletion-sensitive content have the origin send a short `s-maxage` (seconds, not hours), which bounds how long a missed invalidation can matter.
- Restart or upgrade one gateway at a time, and avoid restarting a gateway right after it issued DELETEs. Peer unavailability during a rolling deploy is exactly when queued invalidations are most likely to be pending.
- After any restart or crash of a gateway, re-issue DELETE for critical keys.
- DELETE every canonical key: the key is tenant + path + query, so each query-string variant is a separate key and needs its own DELETE.
- Verify critical removals by reading the key through each gateway, not by the DELETE status alone.

**Not provided:** durable invalidation log, shutdown drain, restart detection, a TTL ceiling. Remediation options under consideration (none approved or implemented) are in `docs/research/phantomcache_milestone_accountability_report.md` section 12.
