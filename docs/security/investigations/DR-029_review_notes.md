## 1. Headline: can a fabricated cluster entry be served over HTTP?

CONFIRMED: not in the code I read. I tried to break it six ways and could not. The isolation holds at two independent levels, which is stronger than the report states (the report argues only the struct level).

Level 1, struct identity. The cache map is keyed by `CacheKey { tenant_id, path, query }` deriving Hash/Eq (`cache.rs:22-27`); lookup is `shard.map.get_mut(key)` (`cache.rs:1259`), in-flight is `shard.in_flight.get(key)` (`cache.rs:1295`). Neither uses the canonical string. The cluster key is `CacheKey::new(None, key, None)` (`node.rs:415`): tenant `__default__`, query `None`, path = raw frame string, rejected if it starts with `/` (`node.rs:419`). The HTTP key is built at exactly two places in `src` (`server.rs:1255` GET, `server.rs:1982` DELETE) after `norm_path` forces a leading `/` (`server.rs:1249-1253`, `1976-1980`). So HTTP path always starts with `/`, cluster path never does; struct equality is impossible.

Level 2, canonical string. `to_canonical_string` is `tenant:path` or `tenant:path:?query` (`cache.rs:96-101`). Cluster canonical always begins `__default__:` followed by a non-`/` char (or empty). HTTP canonical for tenant `__default__` is `__default__:/...`; for any other tenant the tenant segment differs, and tenants cannot contain `:` (`cache.rs:44-51`, alphabet `[A-Za-z0-9._-]`). So even code that compares or parses canonical strings (`from_canonical_string`, `cache.rs:103-116`; peer invalidations `node.rs:535`, `node.rs:83`) cannot confuse them. `":?"` in a path is rejected (`cache.rs:80`) so the path/query split cannot be forged to shift a cluster key into the HTTP space.

## 4. Severity

The investigator's Low-to-Medium is supportable as a bracket, with this split: Low for integrity (no HTTP-visible effect demonstrated, structurally prevented at two levels, authenticated high-privilege precondition); Low-to-Medium for availability and resource effect (eviction of unvisited HTTP entries, entry-slot and byte pressure, counter/telemetry pollution that feeds the intelligence inputs), and in that dimension the marginal gain over DR-027 (a member can already flush every cache) is small. I would phrase the rating as "Low as exploited today; Medium as a latent hazard", not as a single number, and I would not use the register's "high integrity impact".

What would raise it to High:
- Any change that lets an HTTP or other key reach a non-`/` path: removing or reordering `norm_path`, a new route or lab/API handler that calls `CacheKey::new` without it, or percent-decoding/normalisation applied after the leading-`/` rule.
- Removing the `starts_with('/')` guard (`node.rs:419`), or changing the tenant for cluster keys to a real tenant (e.g. tenant-aware peer keys) while keeping the fabricating body. The isolation currently depends on two lines in two files with a test on only the cluster side (M-2); no repo test asserts the HTTP side cannot read the cluster namespace (the report's proposed test 4 fills that gap).
- Peer-fill landing on top of this arm, or a peer-fill that writes into the same keyspace.
- The cluster listener starting without mTLS in a production path, or exposed to a non-trust domain with weak certificate issuance.
- Fabricated bodies being returned to a gateway-internal consumer that trusts `HIT`/`MISS val_node_*` (none found in `src`).
It would drop toward Informational if the arm were confined or removed (Option F/A') and a guard test existed.

## 5. Remediation options and the recommended option

Report's recommendation: F (fabrication only on private-cache nodes; shared-cache nodes get an explicit unsupported error) with A' semantics.

Assessment:
- Correct in direction, and least churn: tests that send GetRequest use `VirtualNode::new` (private cache; M-2 at `m7_sec_round3_tests.rs:332`, KG-6 at `known_gaps.rs:565`), and `new_with_cache` appears in tests only at `known_gaps.rs:113,117` (no GetRequest there), so none of the existing GetRequest tests I read would see a changed outcome (U7 caveat: I did not read all seven files). KG-6 remains valid.
- Weakness 1: the distinction is implicit. "Shared vs private cache" is inferred from which constructor ran (`node.rs:60-65`, `set_cache`). A node that is later pointed at the serving cache by other means, or a test/embedder that uses `VirtualNode::new` and then calls `set_cache`/`new_with_cache`, flips behaviour silently. I would prefer an explicit field (for example `serving_cache: bool` set by both `new_with_cache` and `set_cache`) with a test that asserts the main.rs wiring constructs that node as serving.
- Weakness 2: the check must come before the Recovering/Suspect branch (`node.rs:436`), otherwise a shared node in those states still returns the fabricated body. The report implies "without any cache access" but does not state the ordering.
- Weakness 3: the stub stays compiled and reachable on private nodes. If any production path ever built a listener from `VirtualNode::new`, the exposure returns, but not to the HTTP cache (private cache), so this is acceptable as interim. Eventual deletion (A) is cleaner once the probe tests migrate.
- Side effects I can see: new wire behaviour on shared nodes (an `ERR` reply instead of `MISS val_node_*`); callers such as `forward_key_over_tcp` (`router.rs:1420-1445`) and the router's health logic must tolerate it (U5); any external tooling that probes with GetRequest against a production node would now get an error. A reply of `ERR 400` reuses the existing "rejected" shape, but a distinct code makes the audit story clearer.
- Option C (private cache for the stub) is also viable and small, but still leaves fabricated data on the wire; Option E (config flag) is worse than F because it can be enabled in production; Option D does not remove the problem; Option B is a no-op wrapper as the report says.
- Required tests per the report (1, 2, 3, 5, 7) plus test 4 (HTTP cannot observe the cluster namespace) are the right set. Test 4 passes today and is the cheapest high-value addition because it protects the property the severity rating depends on. Per `CLAUDE.md` section 5/2, any change under `src/dist` needs owner approval, an independent review pass and a test that fails without the change; I did not assess those gates as met.
