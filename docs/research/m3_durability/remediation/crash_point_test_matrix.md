# M3 crash-point test matrix (K1-K21b): design, results, limits

Status: **MEASURED in the sandbox** (`D:\Temp\sbx_m3`): debug build, loopback, one Windows 11 Home host (10.0.26300), `cargo -j 1`, real `phantom-cache-demo` gateway processes with mTLS and a fault proxy on every link, origin `Cache-Control: max-age=120`. NOT measured: release profile, Linux, multi-host, real network faults, power loss. Nothing here is integrated into the main tree; integration is pending independent review and the owner's approval.

Source of the matrix: `docs/research/vision/three_pillar/01_distributed_systems.md` section 6.3 (rows K1-K20), extended by this round (K21, K21b, K22 and the extra properties the brief listed). Test file: `tests/integration/m3_crash_point_tests.rs` (in the patch set; registered with `required-features = ["m3-failpoints"]`). Raw logs: `evidence/`.

## 1. Method and instrumentation

- **Crash points** are compiled in only with `--features m3-failpoints` (off by default; the function `dist::durable_log::failpoint` is an empty inline function otherwise). A gateway whose environment names a point in `PHANTOM_M3_FAILPOINT` terminates itself at that code location with `std::process::exit(137)`: no shutdown path, no drain, no log close, writer thread killed mid-flight. This is the in-process equivalent of kill -9 at an exact location; it is NOT a power cut (OS buffers survive a process exit). Points: `delete.after_local_purge` (server.rs), `router.after_primary_ack`, `router.after_durable_before_dispatch`, `router.after_dispatch`, `router.worker.after_delivery` (router.rs), `log.after_write_before_sync`, `log.compact.after_tmp`, `log.compact.after_rename` (durable_log.rs), `boot.after_replay` (main.rs). `PHANTOM_M3_TEST_COMPACT_MIN_BYTES` (same feature) forces compaction after every batch for K9/K10.
- **External kill** uses the harness `kill_node` (TerminateProcess on Windows, the closest kill -9 equivalent) after the 204 was received.
- **Graceful stop** uses CTRL_BREAK aimed at the child's process group. It worked on this host (the gateway printed `[shutdown] received Ctrl-Break` and exited 0). It needs a console shared with the test runner; under a detached runner the two graceful tests print `GRACEFUL_STOP_NOT_FEASIBLE` and return WITHOUT asserting. Here they asserted.
- **Scenario:** nodes 1 (issuer G), 2 (victim B, G->B link blackholed), 3 (canonical primary of the key: found by scanning with the production router), optionally 4 (A, reachable). Key warmed on every node (v1), origin mutated to v2, DELETE via G, then the crash. Convergence = B (or A) serves v2.
- **Observation window** 10 s (40 s for the storm). The origin's `max-age=120` means a stale entry would outlive every window; the tests never wait for expiry.
- The file/format-level cases (torn tail at every cut, mid-file corruption, bad header, wrong node, size bound) are **unit tests** in `src/dist/durable_log.rs` (21 tests).

## 4. What this matrix does NOT show

- Anything about power loss, Linux, other filesystems, release builds, multiple hosts, or network faults beyond the loopback proxy (blackhole / delay).
- That the failpoints reproduce every real crash timing: a failpoint exits the process at a code location, a real kill can land between any two instructions. The external-kill tests (K5, K13, K14, K17) add real timings, but only at the points the harness chooses.
- Statistics: each test ran once per build (the original reproduction ran 5 times). They are deterministic-by-construction scenarios (blackholed link), not samples of a random process. No confidence intervals are claimed.
- Concurrent DELETE storms above 120 keys, overflow to tenant/full-flush escalation at process level (covered at unit level by `replay_is_idempotent_and_bounded`), and mid-file corruption at process level (unit level only).
