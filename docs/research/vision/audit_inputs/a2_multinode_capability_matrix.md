## 3. Architectural assessment

Labels: **FACT** (verified by me in code or read in a doc and noted), **INFERENCE** (my reasoning from facts), **RECOMMENDATION**, **UNRESOLVED** (could not verify).

### 3.1 What the architecture is

- **FACT** Option A1: independent local caches plus an invalidation bus (ADR-003 s3). One process = one `PartitionedCache` (`main.rs:~200`), one HTTP listener, one cluster listener. The cluster layer carries exactly four message families (`frame.rs:22-31`): GetRequest (stub), Invalidate, Heartbeat, AntiEntropy.
- **FACT** Membership is static, loaded once, `u8` ids, fixed router vector; the registry has a revocation mechanism that nothing in the binary triggers.
- **FACT** Cache state is never shared: the only cross-node effect is deleting entries.
- **FACT** Intelligence, origin cap, byte budget, telemetry are per process.

### 3.2 Can it evolve into the wider distributed vision without major redesign?

**Verdict by sub-vision:**

| Vision element | Evolution path | Redesign needed? |
|---|---|---|
| Reliable cluster-wide invalidation (stronger guarantee) | Add durability, drain, restart detection, tenant/full-flush API, receiver-side scope authorization | **No.** Fits the A1 design; mostly additive (see 3.4). |
| Dynamic membership | Make `router.nodes` an `ArcSwap`/`RwLock<Vec>`, call `registry.update()` from an admin API or file watcher, drive pool eviction from the existing revocation channel; epoch check in anti-entropy already carries `membership_epoch` | **Moderate, not a redesign.** Registry, epoch, revocation, session eviction already exist. Rebalancing is easy because there is no data to move (HRW only picks a DELETE primary). Risk: `membership_epoch` mismatch makes anti-entropy handlers drop connections (`node.rs:~591`), so a rolling epoch change needs a tolerant window. |
| Coordinated reads / peer fill (HRW owner forwarding) | New request-forwarding layer on the GET path; wire needs real GetResponse (status, headers, freshness, tenant, auth, loop-prevention) | **Substantial but contained**: the transport, pool, mTLS, HRW and failure states are reusable; the serving contract (ADR-002), coalescing across hops, hot-key amplification, and consistency model (single owner per key) are new. ADR-001 rates B as "Largest" cost. Not a rewrite of the existing code, but the A1 consistency statements stop applying. |
| Per-tenant quotas / fairness | Per-tenant byte accounting in `cache.rs` + tenant-aware eviction; per-tenant origin cap | **Moderate in single-node code, independent of distribution.** Byte accounting I1-I8 is global (`audit_bytes`); a per-tenant dimension touches the most invariant-heavy module (needs independent review per CLAUDE.md s5). |
| Cluster-wide origin cap / global budget | Needs a shared signal (gossiped counters or a coordinator) | **New subsystem**; nothing exists. Per-process cap is a deliberate simplification, not a fundamental limit: the cap executor is a trait object (`DefaultPolicyExecutor`) and could take a peer-supplied budget. |
| Distributed workload intelligence / predictive pre-warming | Needs (a) a telemetry/signal frame type, (b) aggregation with provenance, (c) a content-bearing fill/prefetch frame, (d) safety gating | **New subsystems on top of reusable transport.** Frame format has an explicit msg_type byte (`frame.rs:22-51`) so adding types is cheap; but the intelligence layer is itself unvalidated single-node (ledger s6), so building distributed versions first is premature. |
| Multi-region/WAN | Different failure model (RTT, partitions, clock) | **Yes, a different design.** ADR-003's "zero clock dependence" is a plus; the 150 ms synchronous primary leg and 250 ms repair cadence are LAN assumptions. |

**INFERENCE (main conclusion):** The current architecture can evolve into a *reliable multi-gateway invalidation cluster with static or semi-dynamic membership* without redesign. It can evolve into *coordinated reads, a shared capacity pool, cluster-wide budgets or distributed intelligence* only by adding new layers; the existing pieces (framing, mTLS identity, pool, HRW, node state machine, ledger, anti-entropy) are reusable, but the consistency story changes from "tombstones + TTL" to something that needs a new ADR and a new test model. No existing component has to be thrown away, but several statements in the docs (G2, G3, "cluster-wide guarantee") would have to be rewritten.

### 3.3 Reusable components (and why)

1. **Framing + codec** (`dist/frame.rs`, 1145 lines): versioned magic, msg_type byte, bounded key length, tested by `security_phase3b_framing_tests` (13). New message types are additive.
2. **mTLS identity and membership registry** (`security/cluster.rs`): per-frame re-validation, fingerprint pinning, revocation channel, epoch. Directly reusable for dynamic membership and for per-peer authorization (add a capability field to `MemberNode`).
3. **Connection pool with epochs and pre-warm** (`dist/pool.rs`, `router.rs:2011`): bounded per-node, evictable on revocation.
4. **Rendezvous router + node state machine** (`router.rs:1351-1418`, `node.rs:10-18`): HRW is the natural owner function for later coordinated reads; states Suspect/Recovering already gate eligibility and GetRequest serving.
5. **Repair ledger with explicit bounds and collapse rules** (`router.rs:137-480`): a good model for "owed work"; design.md for durability mirrors it.
6. **Anti-entropy tracker/ring** (`anti_entropy.rs`): contiguous-ack semantics are model-checked (`protocol_model_tests`).
7. **Per-node generation fencing and epochs** (`core/cache.rs`): the correct local primitive for any later replication (version a fill against an invalidation).
8. **Test harness + fault proxy** (`tests/support/`): the only way multi-node claims are testable today; should graduate to a shipped lab backend (currently dev-only).

### 3.4 Temporary engineering gaps vs fundamental constraints

| Limitation | Class | Reason |

| Static membership, fixed `Vec` of nodes, u8 ids | **Temporary** (static) / **soft constraint** (u8: 255 nodes is ample for this design; changing it touches wire + registry) | |
| `update()` / revocation not wired to an admin surface | **Temporary** | |
| GET local-only, caches independent | **Design decision with consequences** (ADR-003 Option A1; B rejected) | Changing it is a re-architecture of the read path and of the consistency contract, not a patch. This is the one **fundamental constraint** relative to a "single logical distributed cache" vision: capacity does not aggregate, hit ratio does not improve with N, origin load multiplies with N. |
| Invalidation-only coherence (no value propagation, no cross-node version in the frame) | **Fundamental to A1** | Cross-node fill-vs-invalidate races are bounded only by TTL (row 3f, INFERENCE). Fixing it requires either versioned keys on the wire or owner-based reads. |

### 3.5 M3 invalidation durability defect: architecture or unfinished requirement?

- **FACT** Defect reproduced by a prior agent on the current code (`m3_durability/reproduction_report.md` s1,3), consistent with my reading of `main.rs:509-514` and the in-memory structures `RepairLedger`, broadcaster channel, `DestinationSequencer`, ring (`router.rs`).
- **INFERENCE** It does **not** change the architecture. It exposes an unfinished reliability requirement of A1: ADR-003 asserted "Node Restarts: supported" and promised bounded staleness; the sender-side debt is an obligation that A1 inherently creates, and A1 did not persist it. The design stays "independent caches + invalidation bus"; it just requires the bus's issuer to be crash-safe or the receivers to be able to detect an issuer reset.
- **Where the proposed patch plugs in (design.md + diff stats; I did not apply or run it):**
  - New module `src/dist/durable_log.rs` (+1298 lines): append-only CRC-framed log, group-commit writer thread, compaction, boot replay.
  - `src/dist/router.rs` (+152/-2): hooks in `invalidate_key_across_cluster` (append intent after primary ack, before `dispatch_fanout`), `RepairLedger::record`/`mark_full_flush` (note owed), ack sites (`complete`, `drop_permanent`, `flush_finished`, broadcaster `delivered`), a `drain(deadline)` on the router.
  - `src/main.rs` (+74/-5): open log + replay before starting the repair worker; graceful-shutdown sequence (readiness off, drain, `router.stop()`, log close); Windows CTRL_BREAK listener.
  - `src/config.rs` (+7): three env keys (`PHANTOM_INVALIDATION_LOG_PATH`, `_FSYNC`, `PHANTOM_SHUTDOWN_DRAIN_MS`); `src/lib.rs` (+1).
  - Test patch ~778 lines (harness kill/restart/graceful-stop + 5 multi-process tests).
  - ~1.5 kLOC total, **no change to `core/cache.rs`**, so fencing/epoch/eviction invariants (CLAUDE.md s5) are not touched (design D5).
- **FACT (design.md 1, 4.8)** No wire/protocol change: sequences restart at 1, the receiver applies every InvalidateRequest regardless of sequence; a boot id in the frame was explicitly rejected. **INFERENCE:** that means peers still cannot *detect* an issuer restart; durability repairs the debt, not the observability. A peer that pulls from a restarted issuer gets `HistoryOverwritten` and flushes (coarse but safe).
- **FACT (design.md 7, test_plan.md 4)** Not covered: concurrent DELETE+restart, kill during compaction, disk full/read-only, Linux, power loss, independent review. Fail-open on log write errors (owner decision open). DELETE-handler cancellation window between local purge and intent is not addressed.
- **RECOMMENDATION** Treat as a required M3 reliability item before any claim of "bounded staleness in a cluster". It needs: owner approval (CLAUDE.md s2), independent review of the invalidation path (s5), a clippy/whole-suite run (reproduction report s9 says not run), and doc corrections (ADR-003 G2/G3 already amended). Plan for it to be opt-in first (env-gated, as designed).
- **UNRESOLVED** Whether fail-open is acceptable for the product's deletion semantics; whether a shutdown drain without the log is sufficient for planned restarts; behaviour on Unix.

### 3.6 Is single-node-first sequencing sound?

- **INFERENCE** Yes, technically, for three reasons: (1) every distributed guarantee here is a composition of per-node guarantees (fencing, byte accounting, TTL), and the per-node TTL ceiling defect (no gateway cap on origin lifetime) makes any cluster bound meaningless until fixed; (2) the intelligence/origin-cap thread (the main research contribution) acts on the per-gateway fetch path and does not need the cluster (ADR-001 s7 reasoning, [doc]); (3) the cluster layer is already the most defect-dense area (KG-1..KG-6, C-01..C-08 fixed in M3, then a durability defect found afterwards).
- **INFERENCE (caveat)** "Single-node first" must not mean "no distributed design yet": decisions in single-node code that will constrain distribution should be made now: a per-tenant accounting dimension, a key version/generation that could be put on the wire, a stable hash for placement, and a TTL ceiling. Those are cheap now and expensive after N-node features land.
- **UNRESOLVED** Whether the original product vision treats multi-node as a first-class MVP (then sequencing delays a headline) or an extension; the repo's own master context calls it "not a distributed database".

## 5. Top architectural constraints (ranked)

1. **Independent per-process caches; GET is local-only.** No capacity aggregation, no read-through, hit ratio and origin load do not scale with N; cluster = invalidation bus only. (Decision, ADR-003; changing it is a re-architecture of the read path and consistency contract.)
2. **Coherence is invalidation-only and unversioned on the wire.** No cross-node fencing; bounds rest on TTL, and TTL has no gateway ceiling, so "bounded staleness" is not currently a property of the product.
3. **Owed-invalidation state is volatile and issuer-local** (ledger, queues, sequencers, ring); issuer restart is undetectable by peers. Fixable additively (durable log/drain), no protocol change required.
4. **Static membership and no admin surface** for the already-implemented revocation/update machinery.
5. **Failure detection is a by-product of invalidation traffic;** heartbeat does not drive state. `Failed/Offline/Degraded/Joining` have no production semantics beyond the operator flag.
6. **No tenant resource isolation; peer authorization is identity-only** (any member can flush any tenant).
7. **Per-process origin cap and per-process intelligence;** no signal, budget or fill frames in the protocol.
8. **No shipped way to run, observe or fault-inject a multi-node setup** (harness is test-only; no PKI tool; no cluster metrics).

## 6. Verdict

**Evolve, not redesign, for the narrow vision (reliable multi-gateway invalidation cluster): confidence about 80%.** The reusable core (framing, mTLS identity/registry, pool, HRW router, node state machine, ledger, anti-entropy, harness) is sound in structure, and the largest known defect (durability) plugs in additively without wire or core-cache changes. Confidence is capped by: all evidence being loopback/debug/Windows, no independent review of the cluster code, and the unresolved cross-node fill-vs-invalidate race.

**Partial redesign (new layers, same foundations) for the wider vision (shared capacity, coordinated reads, cluster-wide budgets, distributed intelligence, coordinated pre-warming): confidence about 70%.** Not a rewrite: the transport and identity pieces are reusable and the frame format admits new types; but the read path, the consistency contract and the cluster-wide control plane do not exist and cannot be reached by incremental patches to the invalidation bus. Confidence is lower because those requirements are not specified in a repo document I could treat as the vision, and because intelligence benefit is unproven even on one node.

**WAN/multi-region: redesign (confidence about 75%)** because failure model and timeouts are LAN-bound.

Single-node-first sequencing is sound, with the caveat that four cheap forward-compatible decisions (TTL ceiling, per-tenant accounting hook, stable placement hash, key version on the wire) should be settled before the next distributed feature.
