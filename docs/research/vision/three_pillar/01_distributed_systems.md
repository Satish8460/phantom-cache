## 0. How to read this file

**Tags.**
- **FACT** = I opened the file and line cited (or the document cited) and it says this. Facts about behaviour I did not run are facts about code text only.
- **REPORTED** = stated in a repo document or by a prior agent; I did not re-derive it.
- **INFERENCE** = my reasoning from facts. It can be wrong.
- **RECOMMENDATION** = what I propose. Not an approval.
- **UNRESOLVED** = I could not settle it from the evidence.
- **LITERATURE** = general knowledge not verified here against a primary source. Do not use for novelty or correctness claims.

**Status classes (from the brief).** IMPLEMENTED / TESTED / INDEPENDENTLY VERIFIED / UNVERIFIED / PROTOTYPE ONLY / DESIGNED BUT NOT IMPLEMENTED / BLOCKED / RETRACTED. I added one label, **NOT IMPLEMENTED**, for capabilities that do not exist and for which no design existed before this file. "TESTED" always means: loopback, debug build, Windows 11, single host, unless a row says otherwise. No row below reaches INDEPENDENTLY VERIFIED in a strong sense: no cluster code path has had a reviewer who was not its author run it or attack it (`docs/STATUS.md` M3 row: "Independently verified: Partial", reading reviews only).

**Two things that must never be blurred (the owner's mandate).**
1. **Distributed invalidation** = N independent caches plus a bus that deletes entries. This is what exists.
2. **Coordinated distributed caching** = nodes that cooperate on reads, placement, capacity and origin load. This does not exist.
Calling (1) "a distributed cache" in a demo or a claim is the specific mistake this file is built to prevent. Also: product vision drives architecture here. The current implementation limits what may be *claimed*; it does not limit what is *designed*.

**Standing preconditions used by every contract clause (P0).**
- P0.1 The operator changes the origin first, and only then issues the DELETE. If the order is reversed, no cache protocol can help.
- P0.2 After the origin changed, any origin fetch that *starts* later returns the new content (the origin is not itself a stale cache).
- P0.3 Cluster members are authenticated and trusted not to be malicious for the purposes of correctness clauses. Malice is workstream P3's problem; where it affects availability I flag it.
- P0.4 Time: no clause below depends on synchronized clocks across nodes. Freshness (TTL, `Age`, `Date`) is evaluated on each node's own wall clock, which is a separate exposure (section 8).

## 1. Verified current distributed baseline

### 1.1 What the system is, in one paragraph (FACT)
One gateway process = one HTTP listener, one in-memory `PartitionedCache`, and (in the mTLS cluster configuration) one cluster listener. The local cluster node shares the HTTP serving cache (`src/main.rs:332`); remote peers are address-only descriptors forced to `Active` at start with no probe (`src/main.rs:364-367`). GET is served from the local cache only: the router is used by the DELETE handler (`src/api/server.rs:1995`) and nowhere on the GET path. The cluster wire carries eight message types (`src/dist/frame.rs:22-31`): GetRequest/Response, InvalidateRequest/Ack, HeartbeatRequest/Response, AntiEntropySyncRequest/Response. The only cross-node effect on cache content is deleting entries. This is Level A plus part of Level B (definitions in section 2).

### 1.3 Findings that sharpen or correct earlier documents (FACT unless tagged)
1. **A "204" gives no remote assurance for keys whose canonical primary is the issuer.** `route_key` iterates all nodes including the local one (`router.rs:1356`), and `connect_to_node_inner` has no local-node special case (`router.rs:1196-1215`), so the "primary ack" for such a key comes from the issuer's own listener (INFERENCE; not traced at runtime, ADR-001 §8 also left it open). For about 1/N of keys, a 204 means "I purged myself" and nothing else was confirmed synchronously. Every other member is then covered only by the asynchronous path. This matters for clause C2 and for any "acknowledged" wording in the UI.
2. **The receiver does not enforce the membership epoch on InvalidateRequest.** The epoch is echoed into the ack (`node.rs:564`) and the sender compares the echo to its own current epoch (`router.rs:1674`), which is trivially equal. Only the anti-entropy handler enforces it (`node.rs:590-595`). So "membership epoch" on the invalidation path is bookkeeping today, not a guard.
3. **`protocol_model_tests` is weaker than its name suggests.** The "exhaustive fill-vs-invalidate" test permutes four actions on one `PartitionedCache` and asserts only the case initiate < complete < invalidate (`protocol_model_tests.rs:98-106`). The case that matters (invalidate arrives between initiate and complete) is not asserted there; it is covered by single-node tests `test_delete_fences_in_flight_fill_race` (REPORTED). There is no multi-node model.
4. **A2's row 3f inference ("a peer that fetches concurrently with an in-flight invalidation can store the pre-change body after the frame was applied") is not supported by the code I read, for origin fills.** If the frame reaches node Y while Y has an origin fetch in flight, `delete_impl` bumps the key generation and detaches the in-flight entry (`cache.rs:1609-1637`), and `finalize_fetch` refuses to store when `generation != op_gen` (`cache.rs:1463`). The residual cross-node exposure for origin fills is a *missed* frame (the M3 defect), not a fill race. The cross-node race becomes real only when a node fills from a *peer* (Level C; section 4.3). INFERENCE; no multi-process test provokes either case.
5. **Authorization gap with an availability edge (hand-off to P3).** An authenticated member can send Tenant scope with arbitrary tenant ids. `try_invalidate_tenant` falls back to a *global* epoch bump when the tenant table is full at 10,000 entries (`cache.rs:581-593`), so a member can flush every tenant on every peer by sending enough distinct tenant ids (INFERENCE from code; untested). FullCache scope does the same directly (`node.rs:553-558`).
6. **Stale docs.** `docs/research/architecture_trace_m3.md` predates M3: of its gaps, the local node now shares the serving cache (`main.rs:332`), anti-entropy has production callers (`main.rs:375,383`), local purge precedes the cluster call (`server.rs:1990`); the fabricated cluster GET (KG-6) is still present (`node.rs:446-458`). Do not cite its line numbers. ADR-003 says the reconciliation loop runs every 5 s; the code runs it every 250 ms.
7. **Staleness has no gateway ceiling.** Freshness lifetime comes from `s-maxage`, then `max-age`, then `Expires`, else the configured default (`core/freshness.rs:263-276`). `PHANTOM_MAX_STALE_MS` caps only the stale-serving window (REPORTED, ADR-003 amendment). So the sentence "staleness <= TTL_eff <= 24 h" is false as written when the origin sends `max-age=86400000` or `Expires` far ahead.

## 2. Capability levels and the target architecture

### 2.1 Level definitions (RECOMMENDATION: adopt these names; they follow the owner's mandate)
| Level | Name | One-sentence test |
|---|---|---|
| A | Single-node foundation | One gateway is correct, bounded, observable and honest. |
| B | Multi-node foundation (**distributed invalidation**) | N real processes with identity, authenticated messages, reliable and recoverable invalidation, written consistency and failure contracts, and a cluster view. Reads stay local. |
| C | Coordinated distributed caching | Nodes cooperate on reads (peer-fill), placement, capacity, origin protection and tenant allocation, and keep a stated contract under failure. |
| D | Intelligent distributed caching | Cluster-aware observation, prediction, hot-key and flash-crowd detection, coordinated pre-warming and cross-node optimisation, advisory to the deterministic layer. |

A is the base of B; B is the base of C; C is the base of D. Claims at any level need that level's evidence gate (section 9). **C and D are not dismissed.** They are gated by named research and implementation gates, and the gates are written so they can be passed.

### 2.2 Components reused at every level (FACT, section 1.2)
Framing and codec (new message types are additive: the header has a `msg_type` byte and a version byte), mTLS identity and the membership registry (epoch, fingerprints, revocation channel), the connection pool, the rendezvous router and node-state machine, the repair ledger, anti-entropy ring and tracker, per-node fencing, and the multi-process harness with the fault proxy. None needs to be thrown away. The A2 verdict (evolve for B; new layers for C/D; redesign for WAN) agrees with my reading; I would not put percentages on it (A2's "about 80%" and "about 70%" are judgment, not measurements).

### 2.3 What must change per level

**Level B (reliable invalidation cluster).** Additive; no change to `core/cache.rs`.
1. Durable owed-invalidation log and shutdown drain (the M3 patch, after independent review). Section 6.
2. Heartbeat-driven peer state. Today the heartbeat prunes idle connections only. Make the heartbeat a real liveness probe whose result drives Active/Suspect/Offline, and make it carry (a) the sender's *incarnation id* (random value chosen at process start), (b) per destination the highest stream sequence the sender has issued to the receiver, and (c) a clean-shutdown or replay-complete attestation. This is a wire change (HeartbeatRequest payload is empty today: `pool.rs:406-412`), so it needs a protocol-version decision (section 5.5). Purpose: a receiver can then *detect* a restarted issuer and a lost tail of the stream, which the ADR-003 amendment says it cannot do today.
3. Per-peer capability and rate limits for Tenant and FullCache scope (design with P3; section 12).
4. Runtime membership: make `router.nodes` replaceable (read-mostly snapshot such as `ArcSwap` or `RwLock<Arc<Vec<_>>>`), call `registry.update()` from an authenticated admin path, and make the epoch rollout tolerant (accept epoch N and N+1 during a window; today a mismatch closes the anti-entropy connection, `node.rs:590-595`). Section 5.
5. Cluster observability endpoints (per-peer state with provenance, ledger depth, pending debts, sequence gaps, last-ack age, propagation-latency histogram, incarnation, drain status). Every value labelled measured / inferred / unavailable (CLAUDE.md §4). Shared with P4.
6. Operator tooling: cluster PKI and members-file generator that is shipped, not test-only. Dependency question: the generator needs X.509 creation; `rcgen` is a dev-dependency today, so shipping it as a runtime or tool dependency needs owner approval (CLAUDE.md §2). Alternative with no new dependency: a documented script using `openssl`.
7. A TTL ceiling (gateway-side maximum freshness lifetime) so the contract in clause C8 can be true. This touches `core/freshness.rs` and config; it is an owner decision, not a distributed-systems decision, but the contract depends on it.
8. Release-profile multi-host evidence (section 8).

**Level C (coordinated caching).** New layers on the Level B base.
1. **Stable placement** independent of transient health: a fixed, documented hash; owners computed from the *membership epoch*, not from `NodeState`. Today `route_key` skips Suspect/Recovering/Failed/Offline nodes (`router.rs:1358`), so two nodes with different health views compute different owners. That is acceptable for "who must ack a DELETE synchronously" but not for "who owns the data".
2. **A real fill protocol** to replace the stub: `FillRequest`/`FillResponse` carrying tenant (never taken from the peer without checking), canonical key, requester incarnation and membership epoch, loop-prevention hop count, response status, headers needed to cache correctly, remaining freshness (age, not a new full lifetime), validators, and the owner's fence metadata (section 4.3).
3. **Peer-fill on local miss with owner single-flight** (section 4).
4. **Cluster capacity and origin budget** (section 7).
5. **Coordination under failure**: owner down, owner lagging, partition, membership change.
6. **Tenant-aware allocation hooks** (section 7.4; with P3).

**Level D (intelligent distributed caching).** On top of C, gated by P2's single-node evidence.
1. Signal frames (new message types) carrying *aggregates with provenance*, never raw keys across tenants without a privacy decision (P2/P3).
2. Cluster-level hot-key and flash-crowd detection, then coordinated pre-warm using a content-bearing frame, then placement and admission hints, then cross-node optimisation. Each step starts offline on recorded traces, then shadow, then canary, then active, and stays advisory to the deterministic execution layer (CLAUDE.md §6b). Pre-warming across nodes must not be enabled until invalidation durability (B1, B2) is in place, because warming a peer before a lost invalidation increases stale exposure (V4 §5.2, REPORTED; I agree).

## 3. Distributed consistency and failure contracts

### 3.1 Terms and failure model F
- **Issuer** I: the gateway that receives the DELETE. **Canonical primary** P: the node `route_key` returns for the key. **Acting primary**: the first replica used when P fails. **Peer**: any other member. **Accepted DELETE**: the client received HTTP 204.
- **Failure model F (the only one these clauses are written against):** crash-stop of any process (kill -9, power cut of a host is separate); message loss, delay, duplication and reordering on a LAN; partitions that heal; restart of a process with an empty in-memory cache; no Byzantine members (P0.3); no WAN; no disk loss unless stated. Not in F: clock steps, disk full, disk corruption (these appear in the M3 matrix), asymmetric partitions beyond what the fault proxy can express, more than 5 nodes (never exercised).

### 3.2 Clauses
For each clause: **G** = what is guaranteed; **NG** = explicitly not guaranteed; **Falsifier** = the test that could show the clause false; **Status** = established / not established today. "Established" means a test exists whose body was read (by A2 or me) and which is reported passing; it never means independently verified.

**C1. Local read-after-delete.** G: after 204 on I, no later read on I is served the pre-delete body from the cache (local purge precedes any cluster action: `server.rs:1990`; DELETE detaches the in-flight entry: `cache.rs:1636`). NG: nothing about other nodes; a request that coalesced onto a pre-DELETE fetch *before* the DELETE may still receive that fetch's body. Falsifier: linearizability-style history check with concurrent GET/DELETE clients on one node under fault proxy, plus a mutation test that moves the local purge after the cluster call (this reproduces the old C-08). Status: **established** (`test_m3_04a_local_linearizability_immediate_eviction`, `invalidation_contract_tests`; REPORTED).

**C2. Meaning of a 204 in a cluster.** G: local purge done; and P (or the acting primary) acknowledged applying the delete within the 150 ms leg, except when P is I itself, in which case the ack is I's own (section 1.3 item 1). NG: any statement about any other peer. NG: any durability of owed work. Falsifier: blackhole one non-primary peer, DELETE, assert 204 *and* the peer still stale until repair (this characterises the clause, and exists in spirit in `test_h2_*`); a second test kills P between receipt and apply and asserts no 204. Status: **established by code reading and characterisation tests; the "P is I" case is untested** (UNRESOLVED).

**C3. Propagation to live peers.** G (conditional): each peer that stays reachable and non-faulty receives the invalidation by bounded retry (up to 4 attempts, 25 to 200 ms backoff, 150 ms per attempt: REPORTED in `design.md` §3, consistent with the loop at `router.rs:740-760`), and applies it. The ADR-003 bound D_max <= 250 ms is a *healthy LAN target*, not a guarantee. NG: any bound under loss, delay above the retry budget, or load. Measured so far (REPORTED, `claims_ledger.md`): warm loopback, debug build, P99 about 10 to 20 ms; N=1000 max 49.2 ms; cold first use 35 to 117 ms. Falsifier: release-profile, multi-host propagation study with at least N=1000 DELETEs per cell, P50/P99/P99.9/max with confidence intervals, plus delay and loss cells through the fault proxy (section 8). Status: **not established** at LAN or release; established as a *measurement* on loopback/debug only. The "zero stale at 50 ms" statement is RETRACTED.

**C4. Peer offline or partitioned, issuer alive.** G: while I stays alive and within ledger bounds, an unreachable peer is owed the invalidation; after the link heals and the peer is reachable, it is delivered by the repair worker (250 ms tick, 64 entries per tick, `router.rs:58`) and the peer is promoted Suspect -> Recovering -> Active only after debts at or before its ticket are repaired and a pull reconciliation succeeds (`router.rs:2133-2150`). Overflow collapses to a tenant flush and then a full flush: coarser, never silently lost. NG: any bound on staleness *during* the partition other than the entry's remaining freshness lifetime; no guarantee when I dies during the partition. Falsifier: partition one peer for T, DELETE K times, heal, assert convergence and measure time-to-converge versus T and K; vary K past the 1024-entry bound. Status: **established on loopback** (`test_h2_failed_delete_still_invalidates_all_peers_after_heal`, `test_p2_partition_and_recovery`; REPORTED).

**C5. Issuer crash or kill.** G today: none. A peer that had not applied an invalidation owed by a crashed issuer stays stale until its entry expires (REPRODUCED by a prior agent, section 6). G if the durable log is adopted and reviewed: an accepted DELETE whose fan-out is not acknowledged by every non-primary member is re-delivered after any restart of the issuer, until acknowledged or aged out; bound = (time until the issuer restarts) + repair latency; this is eventual, not D_max. NG with the log: disk loss, deleted log and sentinel, a second failure before delivery plus log loss, `fsync` modes other than `always` under power loss, permanently dead issuer. NG in both: anything about a DELETE that did not return 204. Falsifier: the crash-point matrix in section 6.3 (kill at each step of the DELETE and restart). Status: **not established; the defect is reproduced; the fix is a prototype**.

**C6. Graceful shutdown of the issuer.** G today: none (shutdown path drops queued work: `main.rs:509-514`; REPRODUCED the same loss as a crash). G with drain: owed work is delivered within `PHANTOM_SHUTDOWN_DRAIN_MS`, otherwise kept in the log (if on) or reported as lost (if off). Falsifier: stop with a blackholed peer, heal 400 ms later, restart, observe. Status: **not established**; prototype test passed in a scratch copy only.

**C7. Receiver restart.** G: a restarted node has an empty cache, so it cannot serve pre-restart content; it applies later invalidations normally. NG: no warm restart; origin load surge on return. Falsifier: fill, restart receiver while an invalidation is missed, GET after restart must miss. Status: **established by construction** (in-memory cache) and `test_h1_*` (REPORTED).

**C8. Relation of staleness to TTL.** G (the only honest form today): after an invalidation is *entirely* lost to a node, that node can serve the entry until the entry's freshness lifetime ends, plus the stale-serving window if the response allowed it. The lifetime comes from the origin with no gateway ceiling (`freshness.rs:263-276`); the default is 60 s only when the origin gives nothing, and it is a literal `60_000` because `PHANTOM_DEFAULT_TTL_MS` is not wired (CLAUDE.md §5; `config.rs:115` per the project notes). NG: "staleness <= 24 h"; "staleness <= TTL" in any form that hides the origin-controlled lifetime. Falsifier: origin sends `max-age=86400`, invalidation is blackholed forever, measure how long the peer serves the entry. Status: **the honest form is established by code reading; the ADR-003 G3 form is retracted**. Making G3 true needs a TTL ceiling (owner decision D-P1-07).

**C9. Ordering.** G: invalidations are idempotent tombstones; the receiver applies every one regardless of sequence or issuer (`node.rs:499-558`); therefore the *final* state of a key after any set of delivered invalidations does not depend on their order. Per (issuer to peer) stream order is tracked for repair accounting only. NG: any cross-issuer or cross-key ordering; any multi-key atomicity. Falsifier: two issuers deleting the same key concurrently with reordering via the fault proxy; assert both converge. A *delete-then-refill* ordering is protected only by per-node fencing and P0.1/P0.2. Status: **established by code reading; no multi-process reordering test found**.

**C10. Fill versus invalidation across nodes (origin fills).** G (INFERENCE, section 1.3 item 4): an origin fill that began before an invalidation was applied on the same node cannot be stored after it. NG: any protection if the frame is never applied (that is C3 to C5). Falsifier: a multi-process test with a slow origin that returns the old body after a delay while the invalidation arrives mid-fetch; assert the peer's next GET fetches the new body and `stale_writes_prevented` increments. Status: **single-node established; multi-node not tested**.

**C11. Membership, revocation, admission.** G: a frame from a peer whose fingerprint is not in the registry, or whose `active` flag is false, is rejected on every frame, not only at connect (`node.rs:393-406`). NG in production today: there is no path that changes the registry at runtime (row 6), so "revoked" means "the file was edited and the process restarted". Falsifier: end-to-end revocation test through whatever admin path section 5 adds; today only the library-level test exists. Status: **library established; end to end not established**.

**C12. Read semantics under Level B.** G: each node answers from its own cache; a client that always uses one node sees C1. NG: monotonic reads across nodes (a load balancer can move a client between nodes holding different versions); read-your-writes across nodes before C3 completes; linearizability across nodes; any bounded staleness beyond C3 to C5 and C8. Falsifier: LB-flip client test showing version regression across nodes (this *demonstrates* the non-guarantee). Status: **non-guarantee established by design**.

**C13. Authorization of invalidation scope.** G today: identity only (row 1). NG: any limit on which scope or tenant a member may invalidate. Falsifier: a test where a valid member sends FullCache or a 10,001-tenant sequence and the peer is flushed. Status: **non-guarantee; P3 owns the fix**.

**Proposed Level C clauses (not established; they become the acceptance targets for Stage 2):**
- **CC1 Owner-first invalidation.** For every DELETE, the key's owner (computed from the membership epoch) has applied the invalidation before any non-owner is sent the frame, or the owner is marked as owing it and refuses to serve fills until repaired.
- **CC2 Fill fencing.** A fill is registered as an in-flight operation on the requester before the request is sent, so the requester's local fence covers a concurrent invalidation; the owner never serves a cached body that predates an invalidation it has applied.
- **CC3 No fill across placement disagreement.** If requester and owner disagree on membership epoch, the fill is refused and the requester goes to the origin.
- **CC4 No stale resurrection from a lagging owner.** A node that cannot prove it is synchronized (lease expired, gap detected, Suspect or Recovering) refuses to serve fills (the Recovering/Suspect bypass exists today only as a local self-check: `node.rs:435-441`).
- **CC5 No lifetime extension.** A filled entry keeps the original creation time and remaining freshness; peer-fill never gives an entry a longer life than the origin granted.
- **CC6 Failure fallback.** Owner unreachable, slow or refusing: the requester fetches from the origin under its own origin cap, never returns an error caused only by the peer.
Each needs a falsifying test (section 4.6).

## 4. Coordinated reads and peer-fill

### 4.1 Why this is the hinge
Without it, hit ratio does not improve with N, capacity does not aggregate, and a hot key costs N origin fetches per expiry (FACT from design: reads local, caches independent; INFERENCE for the arithmetic). It is also where new consistency hazards appear. It is therefore a research-and-implementation gate, not a patch.

### 4.2 Options
| Option | Read path | Pros | Cons / risks | Consistency interaction |
|---|---|---|---|---|
| O1 Owner-forward (ADR-003 "Option B": every GET goes to the HRW owner) | client node -> owner -> (cache or origin) | Single copy; capacity aggregates; strongest origin protection | Extra hop on most reads; owner hotspots; owner failure becomes a read-path failure; forward loops; coalescing across hops; changes the serving contract (ADR-002) | Strongest: one copy per key, but only if no local copies exist |
| O2 Peer-fill on miss (local cache first; on miss ask the owner; owner serves its cache or fetches once from the origin; requester stores a local copy) | hit path unchanged; miss path adds one hop | Keeps today's hit latency; cluster-wide single-flight per key at the owner; origin load per key ~1 per expiry instead of N | Many copies exist, so invalidation fan-out must still reach everyone (same as today); stale resurrection risk from a lagging owner (CC4); fill/invalidate race (section 4.3) | Needs CC1 to CC6 |
| O3 Hybrid (O2 plus: owner-forward only for keys the owner marks "no local copy", e.g. large or low-reuse) | mixed | Controls local memory duplication | More policy; two modes to test | As O2 for local copies |
| O4 Replicate hot keys (owner or detector pushes hot entries to all or to k nodes) | local hits for hot keys | Removes the owner hotspot | Needs a hot-key detector (Level D) and content-bearing push; each replica is another invalidation target | As O2, plus push-versus-invalidate races |

### 4.3 The cross-node fill-versus-invalidation race, analysed
**Setting.** Origin changed at t0. DELETE issued at I at t1 > t0 (P0.1). I purges locally, then synchronously invalidates the owner O (today: canonical primary P; the sync leg completes before `dispatch_fanout`: `router.rs:1817-1823`), then fans out to the rest.

**Hazard H1: requester Y fills from O before O applied the invalidation.** Possible only if Y's request reaches O before O applied. With owner-first ordering (O applied before any non-owner is told), a Y that learned of the invalidation at t2 asks O no earlier than t2 > O's apply time. A Y that does not yet know of it may still receive v1: that is the same exposure as Y serving its own v1 hit before the frame arrives (bounded by C3). INFERENCE.

**Hazard H2: response in flight when the invalidation lands at Y.** Y registers the fill as an in-flight operation with `op_gen` before sending (CC2). If the frame lands at Y while the response is in flight, `delete_impl` bumps the generation, and Y's `finalize_fetch` refuses to store (`cache.rs:1463`). Closed by the existing local fence, *provided* the fill goes through the same in-flight registration as an origin fetch. INFERENCE from code; must be tested.

**Hazard H3: owner mismatch.** If the issuer's idea of the owner differs from the requester's (health-dependent `route_key`, different membership epochs, an acting primary used because P was Suspect), H1 reopens: Y can fill from a node that was never invalidated first. Fix: placement from the membership epoch only (CC3), invalidation must reach the *epoch owner* regardless of its health state (owed in the ledger if unreachable), and the owner refuses fills while it owes debts (CC4).

**Hazard H4: stale resurrection from a lagging owner.** An owner that missed an invalidation (partition, lost frame) and still holds v1 would re-spread v1 to nodes that already applied the invalidation. This is *worse* than Level B, where a stale node only hurts its own clients. Today the only protection is a local self-check: a node refuses cache hits in the cluster GET handler if *it* is Recovering/Suspect (`node.rs:435-441`), but a partitioned node does not know it is partitioned, because heartbeats do not drive state. So the owner needs a **synchronization lease**: it may serve fills only while it has heard, within a local-monotonic-clock lease L, from every peer (or from the issuers it cares about) a heartbeat whose advertised "issued up to sequence n" equals its own contiguous received sequence, and without an incarnation change. No cross-node clock sync is needed (each node measures elapsed time on its own monotonic clock). Cost: when heartbeats blip, fills stop and misses go to the origin (a hit-ratio and origin-load cost, not a correctness cost). RECOMMENDATION; the lease length L and the false-positive rate are research questions.

**Hazard H5: issuer restart.** A restarted issuer without the log lost owed work; peers cannot tell (ADR-003 amendment). With incarnation ids in heartbeats, a peer sees "issuer restarted" and can drop to a conservative policy (for example flush the tenants that issuer could have touched, or fail fills closed until the issuer proves replay complete). With the durable log, the restarted issuer attests replay completion. The two mechanisms are complementary (section 6.5).

**What a cross-node version on the wire would be.** Option V1 (preferred, smallest): do not version cache entries; instead put an *incarnation id* and *issued-sequence advert* in heartbeats and a *membership epoch* in fill requests/responses (above). Option V2: per-key invalidation versions (issuer id plus issuer sequence acting as a Lamport-style stamp) stored as bounded, time-limited tombstones at each node; a fill response is accepted only if its tag is not older than the requester's tombstone for the key. V2 is heavier (tombstone memory, expiry rules) and is needed only if V1's synchronization lease proves too coarse in measurement. LITERATURE: Lamport clocks, tombstones with time-bounded retention, leases; unverified here; no novelty claim.

**What must be proven before Level C may be claimed (the evidence gate).**
1. A **multi-node protocol model** (explicit state machine or TLA+-style, or an extended exhaustive enumerator) of: owner, requester, issuer, message loss/delay/duplication/reorder, owner lag, membership-epoch mismatch, issuer crash; with invariants "no fill stored after an invalidation of the same key that began before the fill's source copy was read" and "no lagging owner serves". The current model test is single-node and does not assert the in-between case (section 1.3 item 3). Include a seeded-mutation check that each of CC1 to CC4 is necessary (remove it, the invariant fails), in the style of `test_m3_05_seeded_mutation_detection`.
2. **Multi-process tests with the fault proxy** that provoke H1 to H5 with controlled delay (the proxy has Delay and Blackhole modes: `fault_proxy.rs:21-27`).
3. An **independent review** of the fill and fence code (CLAUDE.md §5: changes touching fencing or invalidation require a test that fails without the change and an independent review).
4. **Release-profile, multi-host measurement** of the benefit and the cost (section 8): origin fetches per key per expiry versus N, hit ratio, fill latency P50/P99, owner CPU and bandwidth, behaviour with a dead or lagging owner.

### 4.4 Recommended staged choice (RECOMMENDATION; not approval)
1. **Stage 2 default candidate: O2 (peer-fill on miss)**, because it leaves the hit path and the current invalidation fan-out untouched, adds a measurable origin-load reduction through owner single-flight, and every new hazard is expressible as CC1 to CC6. O1 should not be built first: it changes the serving contract on every read and moves read availability onto the owner. O4 waits for Level D.
2. Build a **shadow mode first**: the requester computes the owner and would-be fill but still goes to the origin; logs agreement and fence metadata. Measures placement disagreement (H3) and owner lag (H4) without risking a stale read.
3. Then enable fills **per tenant or per key prefix behind a flag**, default off, with a kill switch that falls back to origin (CC6).
**Evidence needed to decide between O1, O2, O3:** the benefit and cost measurements in the gate above, on at least 3 physical devices, with a baseline of Level B plus an external load balancer; plus the model results. If O2's origin-load reduction is small for the target workloads (for example because keys are mostly unique), the owner may reasonably decide Level C is not worth its complexity for those workloads; that is a legitimate outcome of the gate, not a failure of the vision.

### 4.5 Placement stability
- **Hash.** Today: `std::collections::hash_map::DefaultHasher::new()` over (key, node_id), cast to `f64` as the weight (`router.rs:1343-1349`, `:1364`). LITERATURE (std documentation, not re-checked): the algorithm behind `DefaultHasher` is unspecified and may change between Rust releases, so two builds can disagree about owners. Casting a `u64` to `f64` drops low bits, making ties possible; ties resolve by node order. RECOMMENDATION: a fixed, documented hash. No new dependency is needed: `ring = "0.17"` is already a runtime dependency (`Cargo.toml`) and `ring::digest::SHA256` is already used for the ring digest (`anti_entropy.rs:173`); truncate a SHA-256 over a domain-separated (cluster id, node id, canonical key) to 64 bits and compare as `u64`. Cost is small for N <= 255 and can be cached per (key) on the miss path only. Decision belongs to the owner (D-P1-03).
- **Versioned membership.** Owners computed from (membership epoch, sorted active node ids). The epoch already exists in the registry (`cluster.rs:309-317`) and in frames (`frame.rs:159-181`).
- **Rebalancing.** With no data movement (peer-fill is lazy), a membership change only changes who is asked on a miss: keys whose owner changed go cold at the new owner. HRW moves about 1/N of keys when one node joins or leaves (LITERATURE: property of rendezvous hashing). During a change window, requester and owner may disagree on epoch: CC3 refuses fills, requests go to the origin. Origin load during rebalancing is the measurable cost.
- **Weights.** `capacity_weight = 1.0` is hard-coded (`router.rs:1363`); per-node capacity weights are a later extension.

### 4.6 Failure behaviour for fills (design)
Owner dead, slow, refusing, lagging, or placement mismatch: the requester goes to the origin under its own cap (CC6). Owner overloaded: bounded per-peer fill concurrency and a fast refusal (`RejectedRateLimit`-style status); the requester treats refusal as miss. Hot key at the owner: owner-side single-flight already collapses concurrent fills; if the owner's serving rate itself saturates, that is the trigger for Level D replication. Loops: a fill carries a hop count of 1; an owner never forwards.
**Tests that could falsify (Stage 2):** kill the owner mid-fill; blackhole owner to requester; owner lags (missed invalidation) and serves; epoch mismatch; owner returns oversized or wrong-tenant body; fabricated body (the existing stub must be deleted or replaced, not extended: `node.rs:446-458`); tenant leakage (requester asks for tenant A, owner must not answer with tenant B); invalidation during fill (H2); restart of owner (cold) causing a fill storm.

## 5. Membership, failure detection, and LAN versus WAN

### 5.1 Static to dynamic (staged)
- **M0 (today):** static file, restart to change.
- **M1: runtime update by an authenticated admin action.** Wire `registry.update()` (already enforces monotone epoch and fires revocation: `cluster.rs:404-440`) to (a) a file re-read triggered by an authenticated admin request or SIGHUP-equivalent, or (b) an Operator-role API. Make `router.nodes` swappable. Revocation then flows through the existing channel to `evict_peer` (`node.rs:205-226`). Test: revoke a node while it sends; its next frame is rejected and its sessions die.
- **M2: join/leave with operator approval.** A joining node presents a certificate whose fingerprint is not yet in the registry; it stays out until an operator adds it (the trust decision stays human or out-of-band; no auto-trust). Join state `Joining` becomes real: not owner, receives invalidations and owes none, until it has pulled state and passes a sync check, then `Active`. Leave: operator marks inactive; owners recompute at the new epoch.
- **M3: coordinated epoch rollout.** Accept epoch E and E+1 for a window so a rolling change does not cut anti-entropy (today a mismatch closes the connection: `node.rs:590-595`). The epoch advertised in heartbeats lets nodes see who is behind.
- **No gossip or consensus is proposed** at Level B or C. The membership source of truth is the operator-signed registry; failure detection is local and per peer. Consensus (Raft-style) would only be justified if Level C needed agreement on owners under partition; the epoch-owner rule plus CC3 avoids that need (INFERENCE; to be tested by the model).

### 5.2 Heartbeat-driven state (design)
Replace connection-pruning-only heartbeats (`pool.rs:360-380`) with a liveness probe per peer:
- Probe every `H` ms over a dedicated or pooled connection; the response must be correlated by request id (the pool already does strict correlation: `pool.rs:432-435`).
- State machine per peer (kept in `NodeState`): `Active` -> `Suspect` after `s` consecutive misses -> `Offline` after `o` further misses or after a revocation; `Offline`/`Suspect` -> `Recovering` on the first success when debts exist or incarnation changed; `Recovering` -> `Active` only after the ledger is drained and a pull reconciliation succeeded (the existing rule: `router.rs:2133-2150`).
- States are derived from *observations* and shown as `inferred` with last-success age, never as `measured` ground truth.
- `Failed` stays an operator/simulation state and must never be produced by a probe.
- Parameters `H`, `s`, `o`, `L` (lease) are tunables whose defaults must come from the LAN experiments, not from this file. UNRESOLVED: values.

### 5.3 Partition handling policy (owner decision D-P1-05)
When a node is isolated, three policies exist: **serve-until-TTL** (today; available, unbounded by the cluster), **lease-clamp** (after the lease expires without hearing from the cluster, serve cached entries only if their remaining freshness is below a small clamp, else treat as miss), **bypass** (miss everything until the cluster is heard again). Lease-clamp turns a partition from "unbounded staleness" into "bounded staleness plus lower hit ratio", at the cost of false positives on heartbeat jitter and a hit-ratio drop during any partition. This trades availability for staleness and must be an explicit, per-deployment setting. I do not recommend a default; the owner should choose after seeing LAN measurements.

### 5.4 Quorum and split-brain
Invalidation correctness does not need quorum: invalidations are idempotent and commutative, so both sides of a partition simply apply what they can and owe the rest. Quorum would matter only for Level C owner agreement (avoided by epoch-owner placement) or for coordinated cluster budgets (section 7.3). No claim of split-brain safety is made; the model should check "two owners for one key during an epoch disagreement" for the fill path.

### 5.5 Protocol versioning
The frame has a version byte (`VERSION_1`, `frame.rs:8`). Heartbeat payload changes, fill messages and signal messages should be introduced as additive message types or under version 2, with a defined behaviour for a v1 peer (ignore unknown types is *not* current behaviour: the handler drops the connection on an unsupported type, `node.rs:661-664`). A mixed-version rolling upgrade therefore needs an explicit design (negotiate once per connection, or gate new types on the registry's advertised capability). Owner decision D-P1-08.

### 5.6 LAN versus WAN / multi-region
**In scope: one L2/L3 LAN segment** (round trips in the low milliseconds; fate-sharing of switch and power domain acknowledged). **Out of scope: WAN and multi-region**, for these reasons: (1) the timeouts and cadences are LAN constants (150 ms sync leg, 250 ms repair tick, `router.rs:1774-1779`, `main.rs:375`); (2) the repair/propagation story assumes partitions are brief relative to TTL; across regions, partitions and long delays are normal and the staleness contract would need different parameters and likely different mechanisms; (3) freshness uses wall clocks, and WAN clock behaviour is a different problem (section 8); (4) no WAN test environment exists; (5) the repo's own master context defers WAN (A2 cites `docs/handoff/01_PROJECT_MASTER_CONTEXT.md` 1.3, REPORTED). WAN is **deferred, not dismissed**: it needs its own failure model, its own ADR and its own evidence gate; the Level B/C clauses must not be quoted for WAN.

### 6.4 Preliminary design review findings (mine; NOT the commissioned independent review)
Method: I read `design.md`, `reproduction_report.md`, `test_plan.md` and, from `proposed_patch_2_src.diff`, the router hooks, `main.rs` hunk, the `State` logic, `Writer::run`, `maybe_compact` and the `open` prologue. I did not compile or run anything. I did not read the rest of `open` (replay classification) or the unit-test bodies. Nothing here establishes that the patch is correct or incorrect.

1. **Cancellation window, widened by the patch (hypothesis, UNVERIFIED).** The new `durable_intent(...).await` sits between the primary ack and `dispatch_fanout` (diff lines 515-516). If the DELETE handler future is dropped while awaiting it (client disconnect; axum behaviour unverified, `design.md` §7.6 admits the same class), the writer thread may still commit the intent (it was already enqueued) but `dispatch_fanout` never runs, so the debt is in the log image but not in the live ledger. It would then be delivered only after the *next restart* replay. Today the same drop loses the fan-out entirely (nothing recorded). RECOMMENDATION: run the cluster leg of the DELETE as a detached task (`tokio::spawn`) so the client's cancellation cannot interrupt it, and have the handler await the task's result. This is a change to `server.rs` and needs the same review.
2. **Ack/stamp logic reads as sound.** I walked the interleaving "DELETE 2 stamped, repair `peek_batch` of an older entry for the same key runs before the ledger lock is taken". The delivery starts after DELETE 2's stamp, so it is processed after the origin change, and clearing DELETE 2's stamp is correct; the `again` flag still keeps the ledger entry (redundant, safe). Other cases I walked (tenant ack versus collapsed entries; flush absorbing intents; `restore_full_flush` with an older `flush_w`) fail safe (extra redelivery). INFERENCE; needs the mutation test and model.
3. **Wall-clock age-out can silently drop debts.** `age_out(now_ms, ...)` uses wall-clock `unix_ms` stamps and runs at replay and compaction (`design.md` §4.4, diff `age_out`). A forward clock step larger than `max_debt_age_ms` (default 7 days) ages out every debt at the next boot. `design.md` §2 lists clock steps as "age-out only"; it does not list "silent debt loss". RECOMMENDATION: record boot counts or a monotonic-safe reference, refuse to age out when the clock moved backwards or forward implausibly, and log every aged-out debt individually. K16 tests it.
4. **`sync_data` failure semantics (hypothesis on Linux).** After a failed `sync_data`, `dirty` stays true and the next batch retries `sync_data` (diff lines 1507-1516). On some Linux filesystems a failed fsync can drop the dirty pages and a retry can then succeed without the data being on disk. If so, later intents would report "durable" while earlier ones are lost. RECOMMENDATION: after any fsync error, mark the log degraded permanently and rotate to a freshly written file from the in-memory image; verify on Linux. LITERATURE-level concern; UNVERIFIED here.
5. **Partial `write_all` leaves garbage mid-file.** On write error the code does not truncate to `file_len` before the next append (diff lines 1487-1499), so a later successful append lands after garbage and the next boot sees mid-file corruption, i.e. `CorruptFallbackFlush` (a full flush of every peer). Safe but coarse; the disk-full test (K15) should assert the exact outcome.
6. **Fail-open is weakest under load.** `append_intent` returns `Err` when the 8,192-slot command channel is full (diff lines 1375-1378) and the DELETE proceeds. The log therefore stops protecting exactly when the system is busiest. At minimum surface it as a cluster-visible degraded state and count it; fail-closed (5xx when the intent cannot be persisted) is the alternative and is an owner decision (`design.md` §8.1). Note a 5xx after local purge and primary ack does not undo them.
7. **Windows durability of the compaction rename is unverified.** `sync_parent` is a no-op off Unix (diff line 1181). Process-crash safety does not depend on it; power-loss safety of the rename on NTFS is not established here.
8. **Debts for departed members.** Replay re-queues debts by peer id; if membership changed (peer removed) the ledger keeps a debt that can never be delivered until age-out. Needs a rule tied to the membership epoch.
9. **Replay amplification.** Replayed Tenant or FullCache debts flush the whole tenant or cache on the peer on every restart until acknowledged. A crash-looping issuer with a large owed set repeatedly flushes peers. Needs a rate limit or a "replay once per incarnation" rule (K11 plus a loop test).
10. **What the patch cannot fix by design (FACT, `design.md` §4.8):** peers still cannot detect an issuer restart, because no wire change was made and sequences restart at 1. The durable log repairs the *debt*, not the *observability*. Section 5.2's incarnation id is the complementary piece.
11. **Reproduction independence.** The defect reproduction and the fix were produced by the same agent. The failing-before/passing-after structure is sound (`run_failing_before_kill9_log_OFF_01.log`), but the independent review should re-run K1, K4 and K5 itself.

### 6.5 Fail-open versus fail-closed, and what each implies
| Aspect | Fail-open (prototype) | Fail-closed |
|---|---|---|
| DELETE when the log cannot persist | 204 as today; contract degrades to "in-memory only"; visible in log stats | 5xx (a new error variant and handler mapping); local purge and primary ack have already happened |
| Availability of deletion under disk trouble | Preserved | Lost |
| Honesty of 204 | Weaker: 204 may not be durable | Stronger: 204 implies durable intent |
| Client behaviour | Unchanged | Clients must retry; retries are idempotent |
| Recommendation | Acceptable only if degraded state is surfaced to operators and the UI, and documented | Preferable for deletion-critical deployments; make it a setting |
Neither is a default I recommend without the owner's statement of what a DELETE must mean (D-P1-02).

### 6.6 Interaction with fencing and tenant epochs
No change to `finalize_fetch`, generations or lock order is proposed (design D5; diff touches `router.rs`, `main.rs`, `config.rs`, `lib.rs` and a new module). The interaction that does exist is item 9 above (epoch bumps on peers from replayed scopes) and the fact that a log replay delivers *invalidations*, which are always safe with respect to fencing (they only remove). Nothing in the log can cause a stale write.

## 7. Cluster resource management and origin protection

### 7.1 The multiplication problem (FACT)
Byte budget, entry cap and origin concurrency cap are per process (`PHANTOM_MAX_CACHE_BYTES` default 256 MiB, `PHANTOM_ORIGIN_CAP_*`, `DefaultPolicyExecutor::new(Some(cache))` bound to the local cache: REPORTED by A2 with `main.rs:467-480`). With N independent nodes: capacity does not aggregate; the origin can see up to N times the configured cap and up to N fetches per hot key per expiry. A cluster-wide origin budget does not exist.

### 7.2 Options
| Option | Idea | Pros | Cons |
|---|---|---|---|
| R1 Per-node share (static) | Configure `cap_cluster / N_configured` per node | No coordination; conservative; trivial to test | Wasted headroom with skewed traffic or lost nodes; operator must keep N right |
| R2 Membership-aware share | Each node computes `cap / N_active` from its own view | Adapts to node loss | Under partition each side sees a smaller N and uses a bigger share: the total can exceed the cap (up to about 2x for a two-way split) |
| R3 Owner-concentrated origin access (Level C) | Only the key's owner talks to the origin (peer-fill); cap applies at owners | Removes N-fold miss amplification structurally | Depends on Level C; owner skew concentrates load |
| R4 Lease-based budget | A coordinator or elected node hands out concurrency tokens | Tight cluster cap | Coordination, failure of the coordinator, partition behaviour: a new subsystem |
| R5 Gossiped utilisation with AIMD | Nodes share load and back off | No single coordinator | Convergence and stability to be proven; telemetry frames needed |
RECOMMENDATION: R1 as the Level B answer (document it as the honest cluster behaviour), R3 as the Level C structural answer, and treat R4/R5 as Level D research that needs P2's evidence that the single-node cap controller works (the sealed M6 run found H1 NOT_SUPPORTED, `docs/STATUS.md`).

### 7.3 Cluster capacity under Level C
Peer-fill with owner copies and local copies means memory is used twice for hot keys. Capacity accounting needs a distinction between "owned" and "replica" bytes, plus an admission rule (do not store a local copy of a fill if the entry is large or low-reuse: option O3). Eviction stays local and faithful; no cross-node eviction coordination is proposed.

### 7.4 Tenant-aware allocation hooks (coordinate with P3)
Hooks I need from the single-node design so that cluster semantics are possible later: (1) per-tenant byte and entry accounting inside the existing invariants I1 to I8 (the most invariant-heavy module: independent review required); (2) per-tenant origin-concurrency sub-caps; (3) a tenant tag on every fill, signal and invalidation frame (already present in the canonical key for invalidation); (4) per-tenant counters exposed to the cluster view; (5) a rule for what a cluster-level tenant quota means: total quota Q split as `Q/N` per node (simple) or as owner-weighted (Level C). I assume (5) starts as `Q/N` unless P3 says otherwise. Tenant epoch bumps are cluster-visible events (a Tenant-scope frame flushes that tenant on every node): P3 should decide who may send them (section 1.3 item 5).

## 8. Multi-host validation plan

**Rule (CLAUDE.md §4):** keep results separate and labelled: LOOPBACK (N processes, one host), SINGLE-HOST VM/WSL2/container, LAN-PHYSICAL (separate devices, one switch), SIMULATED. 5. **Level C only:** origin fetches per key per expiry versus N; hit ratio; fill latency; owner CPU and bandwidth; dead and lagging owner; membership-change origin surge. Baseline: Level B plus an external load balancer, same workload and seed.
6. **Clock skew.** Record NTP offset on each host before and after each run; run one deliberate-skew experiment (hosts offset by a controlled amount) to show the effect on freshness (`Date`/`Age`, JWT `exp` with 10 s leeway: REPORTED in V3). Claim nothing about skew beyond what is measured.

**Limits to state with every result:** one switch, one site, wired only, at most the node count tested, Windows or Linux as run, no WAN.

## 10. Risks and unresolved questions
1. **Single-author evidence.** Every cluster test, the M3 reproduction and the patch were produced by agents in the same workflow; no independent reviewer has attacked them. All results are Windows, loopback, debug, at most 5 nodes (UNRESOLVED how they behave elsewhere).
2. **The "P is I" 204** (section 1.3 item 1) is inferred from code, not traced. UNRESOLVED until a test shows the local primary case.
3. **Heartbeat and lease parameters** are unknown; false positives could make partition-mode policies harmful. UNRESOLVED.
4. **Peer-fill benefit is unproven.** If target workloads have low key reuse, Level C may not pay. UNRESOLVED; the gate is designed to answer it.
5. **Lagging-owner resurrection (H4)** is the most dangerous new hazard of Level C; the lease design is mine and untested.
6. **Protocol evolution** (v1 peers drop the connection on unknown types: `node.rs:661-664`) makes rolling upgrades a design problem.
7. **Hash stability across builds** is unverified; `DefaultHasher` behaviour is LITERATURE only.
8. **Windows and Linux durability semantics** for the log differ (fsync, rename, CTRL_BREAK); Linux never run.
9. **Time:** freshness is wall-clock; JWT `exp` has 10 s leeway; no clock-fault tests exist (V4 §6.4). A clock step can also defeat the log's age-out (6.4-3).
10. **Fabricated-cache-entry surface** in the cluster GET stub (section 1.2 row 21) should not remain reachable by members once an owner or P3 review confirms it.
11. **Cancellation safety** of the whole DELETE cluster leg is an existing weakness the patch widens (6.4-1).
12. **Demo honesty:** the `NODE_FAILURE` control, three placeholder nodes and any UI node map must be labelled simulated/logical (V3/V4, REPORTED). A node map that implies coordinated caching at Level B would be a false claim.
13. **Scale limits:** `u8` node ids (255), replicas limited to primary plus 2 for failover ranking, per-peer pool and queue bounds; churn above 5 nodes was never exercised.
14. **Original vision source missing.** The only source for the original distributed rationale (a ChatGPT export) is missing (audit §3, §9 item 8). The levels here are a design consistent with the owner's mandate, not a recovery of the original requirement.
