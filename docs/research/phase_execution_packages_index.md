## 4. Common Execution Rules (CER) — apply to every phase unless a package adds stricter ones
**CER-1 Authorization.** A package is PROPOSED until the owner authorizes its execution in writing. AG begins with step E0 (entry verification) and does nothing else before E0 passes. No package authorizes the next one.
**CER-2 Entry verification (E0, every phase).** Before any change AG (a) records HEAD, branch, `git status --short`, stash/staged counts; (b) compares with the previous phase's final recorded state and the package's "starting assumptions"; (c) re-reads the previous completion report and records the **real** results the package depends on; (d) lists assumptions that no longer hold. Any difference not explained by the previous phase's ledger ⇒ STOP (owner decides). Starting assumptions marked PROVISIONAL are re-validated here; a failed assumption triggers the package's stated contingency or a STOP.
**CER-3 Git and working-tree safeguards.** Same prohibitions as Phase 1 §4 rule 7: no `add/commit/push/tag/stash/reset/clean/checkout/restore/rm/mv` on tracked content, no `git worktree`/branch operations, no `cargo fmt`/`fix`/`clippy --fix`, no `npm ci` in `ui/`, no deleting files. Before the first modification of each phase AG creates a **new** snapshot using Phase 1 §6.1 (owner-only directory, secret screening, filtered metadata, byte-exact copy of the non-ignored tree, V1–V3 verification script) at `phase<N>-<UTC>-<shortHEAD>` under the snapshot root, never reusing a directory. A change ledger (`phase_<N>_progress.md` §Ledger) classifies every file touched; an unledgered change is UNEXPECTED and blocks the gate. The only files an agent may modify are those the package lists as authorized.
**CER-4 Result semantics (acceptance criteria, tests, benchmarks, experiments).**
- **PASS** — the check ran as specified, its evidence is attached, and the stated condition holds.
- **FAIL** — the check ran validly and the condition does not hold. A FAIL of a *blocking* criterion blocks the gate; the report states impact.
- **BLOCKED** — the check could not run validly (missing prerequisite, tool failure, environment unfit, stop condition pending an owner decision). Never converted to PASS; blocks the gate unless the owner records a waiver naming the criterion.
- **NOT RUN** — deliberately omitted (e.g., deferred per package, time budget). Allowed only where the package says so; reported with the reason; counts as non-PASS for blocking criteria.
- **A passing test suite is never itself evidence of a distributed or statistical claim.** A benchmark that completed is not thereby valid (see CER-5).
**CER-5 Measurement integrity.** Provenance values: `measured`, `derived`, `simulated`, `inferred`, `unavailable` — an unavailable metric is never represented as `0`, `null`-as-zero or a substitute; simulation results are never reported as system measurements; every figure carries its class — **VALID** (≥10 process-level repetitions where timing is involved, FIT within the stated interval bound, complete manifest, source/tree hash equal before and after, environment checks passed), **EXPLORATORY** (3–9 repetitions or not FIT; never used for decisions), **UNFIT**, **INVALID**, **NOT RUN**. n is never reduced below 10 to meet a time budget: drop items instead. Measurement validity is judged independently of the performance outcome; negative and inconclusive results are preserved. Candidate results never contaminate baseline measurements (separate processes/arms, labeled counters, A/A noise checks). Every run records tool versions, configuration hash, workload parameters and seeds, platform label (`windows-native`, `wsl2`, `linux-host`, `multi-host`), hardware/OS, limitations text.
**CER-6 Decision authority.** *Owner-reserved (always):* architecture changes beyond a package's stated decision points; any new **runtime** dependency; any new **dev**-dependency not already named as pre-approved in the package; destructive or irreversible cleanup; breaking API/schema/wire-protocol changes; changing user-visible defaults; enabling any intelligence mode above `off` by default; waiving or reinterpreting any stop condition or acceptance criterion; commits/pushes/tags; publishing claims; installing software outside user space; touching files outside the package's authorized list. *Agent-permitted (document in the progress log):* naming, file organization within authorized paths, test structure, internal data structures of new code, benchmark parameter ordering within the package's rules, choice among equivalent crate versions already approved, documentation wording, retry of transient tool failures.
**CER-7 Stop and resume.** On any stop condition the agent halts the affected steps (others may continue only if the package says they are independent), writes a **Blocker Report** to the progress log (what, evidence, affected steps, options considered, recommendation) and notifies the owner once. Work resumes only after a written owner decision, recorded with date and scope. A waiver applies to the specific instance only. After resuming, AG re-runs E0 checks that the blocker could have invalidated and records them.
**CER-8 Progress log and completion report.** One live log per phase: `docs/research/phase_<N>_progress.md` (goal, architecture, decisions, step table, ledger, commands/results, tests, measurements, deviations, risks, next steps — in plain English; no duplicate logs). At the end, `docs/research/phase_<N>_completion_report.md` with six separated sections — **Verified facts**, **Measurements and test evidence**, **Inferences and hypotheses**, **Known limitations**, **Deferred work**, **Decisions requiring approval** — plus the acceptance table (PASS/FAIL/BLOCKED/NOT RUN with evidence pointers), file inventory, `phase_<N>_changes.patch` (phase hunks only), dependency appendix, and "next phase: proposal only".
**CER-9 Evidence storage.** Raw data and logs: `bench-results/` (M1–M3) and `lab-results/` (M4–M6), untracked; summaries in the completion report; each artifact hashed in the run manifest; no secrets in any record.
**CER-10 Secrets and privacy.** No environment values, tokens, keys or request bodies in logs, manifests or screenshots; report `path:line:class` only.
**CER-11 Cross-checks at every exit gate.** The research lead reviews the completion report against the package; the owner decides ACCEPT, bounded remediation, or redesign. Remediation passes follow the same CER.
